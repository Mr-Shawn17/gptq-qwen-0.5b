## 0. 五分钟版结论

### 0-1 这条路线的本质

用 **GPTQ 算法**（128 条样本校准 + Hessian 二阶补偿）把 BF16 权重量化成 4bit，产物是**标准 HF-GPTQ 格式**（`qweight/qzeros/scales/g_idx` safetensors + `quantize_config.json`）。这个格式是业界最通用的 GPU 量化格式：vLLM、Transformers、SGLang 直接加载，TRT-LLM 也认（可选阶段 5）。量化是一次性离线过程，不训练、不动原模型。

### 0-2 为什么能落地（全部实测/官方证据，非推断）

| # | 证据 | 来源 |
|---|---|---|
| 1 | vLLM 官方量化支持矩阵：**GPTQ × Turing = ✅** | docs.vllm.ai 官方文档 |
| 2 | 本机 vLLM 0.8.5 源码 `GPTQConfig.get_min_capability() = 60`，GTX 1650 是 SM75，远高于门槛；GPTQ kernel（exllama 等）**预编译在 vllm wheel 内**，无需 nvcc | grep 本机源码实测 |
| 3 | **Qwen 官方已发布 `Qwen2-0.5B-Instruct-GPTQ-Int4`**（ModelScope 可下，auto_gptq 0.6.0 产物）——先拿它验证 vLLM 全链路，排除自产产物变量 | ModelScope 实查 |
| 4 | 量化工具 GPTQModel（AutoGPTQ 维护继任者）官方支持 **Turing sm_75+**，清华源在列（7.6.0 等）；GPTQ 量化算法本身只依赖 torch 矩阵运算（算 Hessian），**不需要 CUDA toolkit**（本机无 nvcc 不构成障碍） | GitHub README + pip index 实查 |
| 5 | `~/bin/start_vllm.sh` 支持 `MODEL_DIR` / `SERVED_NAME` 环境变量覆盖——GPTQ 模型目录传入即用，零脚本改动 | 读脚本实测 |

### 0-3 与 RTN 路线的核心区别（为什么这条更符合你的诉求）

| 维度 | TRT RTN（旧方案 A） | **GPTQ（本方案主线）** |
|---|---|---|
| 产物格式 | TRT 私有 checkpoint，**只有 TRT 认** | **标准 HF-GPTQ，vLLM/Transformers/SGLang/TRT 通吃** |
| 精度 | RTN 直接截断，无补偿 | 校准 + Hessian 补偿，困惑度涨点通常 <4% |
| 校准数据 | 不需要 | 需要 128 条（本方案三选一，含零下载兜底） |
| 新环境 | 不需要 | 需要 1 个（~7GB，ext4 放心装） |
| 耗时 | ~10 分钟 | ~60-90 分钟 |
| 质量对照 | 只能对照 FP16 | 可对照 FP16 + **Qwen 官方 GPTQ-Int4 产物** |

```
阶段 5（可选）：同一份自产产物转 TRT 引擎（int4_gptq）——一份产物，两个引擎
```

### 0-5 验收标准（冻结）

1. vLLM 成功加载自产 GPTQ 模型并起 OpenAI 服务；
2. 5 题质量对照：自产 GPTQ 相对 FP16 **无新增错误**，且与官方 GPTQ-Int4 表现一致；
3. `quantize_config.json` 参数正确（bits=4 / group_size=128 / desc_act=False，与官方产物对齐）；
4. 性能数据三件套记录在案（TTFT / 解码速度 / 显存峰值），与 FP16 基线同口径可比。

> 预期管理：GPTQ 模型文件约 **700-750MB**（不是 350MB——embedding 和 lm_head 共约 545MB 保持 FP16 不量化，这是 GPTQ 标准做法，与官方产物一致）；显存收益约省 200MB 权重；速度以实测为准（0.5B 模型是 launch 开销主导，预期与 FP16 ±15% 内）。

## 4. 阶段 2：GPTQ 量化实施（约 10-20 分钟，GPU 上跑）

### 4-1 量化脚本

保存为 `~/quant_gptq/quant_gptq.py`（gptq 环境运行）：

```python
"""
Qwen2-0.5B-Instruct GPTQ 4bit 量化
参数与 Qwen 官方 GPTQ-Int4 产物完全对齐：bits=4 / group_size=128 / desc_act=False
校准集三选一，默认中文维基（见 CALIB 变量）
"""
import os
from gptqmodel import GPTQModel, GPTQConfig

MODEL_DIR = os.path.expanduser("~/models/Qwen2-0.5B-Instruct")            # 公有源模型，只读
OUT_DIR   = os.path.expanduser("~/quant_gptq/models/Qwen2-0.5B-Instruct-GPTQ-Int4-local")

CALIB = "zh_wiki"   # 可选: "zh_wiki" | "c4_en" | "builtin"

# ---- 校准数据（128 条，gptqmodel 内部会 tokenize 成 tensor 列表）----
if CALIB == "zh_wiki":
    from datasets import load_dataset
    os.environ.setdefault("HF_ENDPOINT", "https://hf-mirror.com")   # HF 镜像
    ds = load_dataset("wikimedia/wikipedia", "20231101.zh",
                      split="train", streaming=True)
    calib_data = [next(iter(ds))["text"][:1024] for _ in range(128)]
elif CALIB == "c4_en":
    from datasets import load_dataset
    os.environ.setdefault("HF_ENDPOINT", "https://hf-mirror.com")
    ds = load_dataset("allenai/c4", data_files="en/c4-train.00001-of-01024.json.gz",
                      split="train", streaming=True)
    calib_data = [next(iter(ds))["text"][:1024] for _ in range(128)]
else:  # builtin：零下载兜底——用本地文档拼接（部署手册 + 方案文档切段）
    import glob, re
    texts = []
    for f in glob.glob(os.path.join(calib_dir, "*.md")):
        t = open(f, encoding="utf-8").read()
        for para in re.split(r"\n{2,}", t):
            if 100 < len(para) < 2000:
                texts.append(para)
    calib_data = (texts * 8)[:128]

print(f"校准样本 {len(calib_data)} 条，首条预览: {calib_data[0][:60]}...")

# ---- 量化（BF16 原生加载到 GPU，逐层 Hessian 校准）----
quant_config = GPTQConfig(bits=4, group_size=128, desc_act=False)
model = GPTQModel.load(MODEL_DIR, quant_config)
model.quantize(calib_data, batch_size=1)
model.save(OUT_DIR)

# ---- 冒烟自测（同进程，backend 自动选）----
out = model.generate("中国的首都是", max_new_tokens=16)
print("冒烟输出:", model.tokenizer.decode(out[0]))
print("产物目录:", OUT_DIR)
```

```bash
conda activate gptq
mkdir -p ~/quant_gptq/logs
python ~/quant_gptq/quant_gptq.py 2>&1 | tee ~/quant_gptq/logs/quant_run.log
```

> 显存预算：BF16 模型 988MB + 逐层 Hessian 工作区 < 1GB，合计 <2.5GB ✅；量化期间先确认 vLLM/TRT 服务已停。

```bash
# GPTQ 模型 → TRT checkpoint（脚本 choices 里明确支持 int4_gptq）
python convert_checkpoint.py \
    --model_dir ~/quant_gptq/models/Qwen2-0.5B-Instruct-GPTQ-Int4-local \
    --dtype float16 \
    --weight_only_precision int4_gptq \
    --output_dir ~/quant_gptq/trt/w4a16_gptq/ckpt/1-gpu 2>&1 | tee ~/quant_gptq/logs/trt_convert.log

# 建引擎（图灵卡同样必须 --context_fmha disable）
trtllm-build \
    --checkpoint_dir ~/quant_gptq/trt/w4a16_gptq/ckpt/1-gpu \
    --gemm_plugin float16 \
    --context_fmha disable \
    --max_batch_size 1 --max_seq_len 2048 \
    --output_dir ~/quant_gptq/trt/w4a16_gptq/engine/1-gpu 2>&1 | tee ~/quant_gptq/logs/trt_build.log

# serve（复用 TRT 启停脚本）
ENGINE_DIR=$HOME/quant_gptq/trt/w4a16_gptq/engine/1-gpu \
MODEL_NAME=1-gpu \
    bash ~/bin/start_trtllm.sh
```

> 依据：weight-only 量化插件 .so 实测含 24 个 sm_70 cubin（见旧方案证据 1），W4A16-GPTQ kernel 与 RTN W4A16 共用同一插件库；`int4_gptq` 在转换脚本 choices 中实查在列。

## 9. FAQ

**Q1：为什么产物是 ~743MB 而不是 ~350MB？**
GPTQ 标准做法只量化 Transformer 层权重；`embed_tokens`（151936×896）和 `lm_head` 保持 BF16。TRT 路线的 350MB 是因为 TRT checkpoint 格式与 tokenizer/嵌入布局不同，不具可比性。

**Q2：速度会比 FP16 快吗？**
不保证。0.5B 模型瓶颈是 kernel launch 开销而非带宽，W4A16 的显存带宽优势发挥不出来。本路线的核心收益是**格式通用性**（一份产物 vLLM/Transformers/SGLang/TRT 通吃）+ 量化质量（GPTQ 带 Hessian 补偿）+ 学习价值（完整校准量化流程）。速度以阶段 4 实测为准。

**Q3：为什么用 gptqmodel 而不是 auto-gptq？**
AutoGPTQ 已归档（最后版 0.7.1，2024-05），GPTQModel 是其官方钦定维护继任者，Turing sm_75+ 一级支持、支持 ModelScope 数据源、持续修 bug。官方 Qwen GPTQ 产物虽是 auto_gptq 产的，但**产物格式完全同一标准**，互认。

**Q4：量化过程会用到 GPU 吗？**
会（BF16 前向算 Hessian），<2.5GB 显存，与现有服务互斥——量化前先 stop 所有服务。

**Q5：desc_act 为什么选 False？**
与官方产物对齐（可比性）；且 TRT-LLM 的 `int4_gptq` 转换要求 `desc_act=False`、`group_size=128`，为阶段 5 留路。
